## 1. Цель проекта

Построить на одной рабочей станции мини-инфраструктуру для прохождения **полного цикла DevOps-практик** (сеть → серверы → приложения → CI/CD → наблюдаемость) с возможностью **включать/отключать слои** по мере необходимости, чтобы не упираться в лимит ОЗУ.

Параллельно — обкатать **гибридный цикл «облако планирует / локальная модель исполняет»** и вести базу знаний для построения личной карты навыков и поиска работы.

## 3. Архитектура гибридного цикла

**Роли:**
- **Облачная модель (Plan + Verify):** `deepseek-v4-flash` (1M контекст, $0.025/$0.051) — планирование, разбор ошибок, верификация
- **Локальная модель (Act):** `qwen3.5-9b-deep` — исполнение, рутина, приватные задачи, импортозамещение
- **Fallback:** при провале локальной — возврат в Plan mode, облако корректирует план

**Механизмы:**
1. **Plan/Act с разными моделями** в Cline (нативный, базовый уровень)
2. **Memory Bank** в `.clinerules/` (6 файлов) — постоянная память между сессиями
3. **Auto Compact + `/smol` + `/newtask`** — управление окном контекста
4. **`@`-упоминания файлов** — точечная загрузка контекста
5. *(позже)* **`llm-orchestra`** в `/data/stands/llm-orc/` — автоматический DAG-цикл с bounded retry

**Правила поведения:**
- `.clinerules/devops-standards.md` — 4 правила (порты, изоляция, уборка, KB)

## 4. Слои инфраструктуры и выбор компонентов

### 🌐 Сетевой слой: **GNS3** (старт), EVE-NG/PNETLab (позже)

- **GNS3** — лёгкий старт: сервер на хосте + опциональная VM 4 ГБ для тяжёлых образов
- **EVE-NG CE / PNETLab** — только когда GNS3 станет тесно; 8–16 ГБ VM
- **Зачем:** маршрутизация, VLAN, ACL, основы сетей
- **Стенд:** `/data/stands/network-lab/`

### 🖥 Серверный слой: **KVM/libvirt**

- Nested virtualization **обязательна** для запуска GNS3/EVE-NG внутри KVM
- Проверка: `cat /sys/module/kvm_amd/parameters/nested`
- Включение: `options kvm_amd nested=1` в `/etc/modprobe.d/kvm-amd.conf`
- Установка: `libvirt libvirt-kvm libvirt-qemu qemu-kvm virt-manager`, пользователь в группу `vmusers`

### ⚙️ Слой приложений: **k3s в KVM**

- **k3s в KVM (3 ВМ)** — основной выбор: 1 server (2 ГБ) + 2 agent (2 ГБ) = **~6–8 ГБ**
- **k3d в Podman** — лёгкий резервный режим, когда память в дефиците
- **Почему k3s в KVM:** полноценные nodes, taints, scheduling — глубже для обучения, чем k3d
- **Стенд:** `/data/stands/k3s-lab/`

### 🔄 CI/CD-слой: **Jenkins + Argo CD**

- **Jenkins (LTS)** — ~2 ГБ, ставится как pod в k3s или контейнер; классический CI
- **Argo CD** — ~2 ГБ, в k3s; GitOps-доставка
- **GitLab CE — отклонён** для основной станции (4+ ГБ минимум, на практике 8–16 ГБ). Альтернатива: **GitLab.com SaaS + GitLab Runner локально**
- **Стенд:** `/data/stands/cicd-lab/`

### 🗄 Слой сервисов

- **PostgreSQL** — StatefulSet в k3s с local-path PVC (k3s включает по умолчанию)
- **Redis** — Deployment
- **Ingress** — Traefik (в k3s по умолчанию) или nginx-ingress для практики
- **Prometheus + Grafana** — позже, когда кластер стабилен
